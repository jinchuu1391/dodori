01개요와 범위

한 줄 정의. 내 mp3 음원을 브라우저에서 열어, 파형 위에서 A-B 구간을 지정하고, 그 구간을 원하는 방식(느리게 · 반복 횟수 · 쉬는 틈 · 키 조절)으로 반복 연습하는 도구.

핵심 가치

  • 정밀한 구간 반복 — 이음새가 매끄러운 루프로 같은 소절을 지치지 않고 돌려 듣기.
  • 집중 드릴 — 어려운 부분만 떼어내 근육 기억이 생길 때까지 반복.
  • 내 몸에 맞추기 — 속도는 늦추되 음정은 유지, 키는 내 음역대로 이동.

타깃 사용자

혼자 노래·보컬을 연습하는 사람. 학원 없이 원곡을 반복하며 특정 파트(고음, 브릿지, 랩 벌스)를 파는 사용자.

03화면 구조

화면은 크게 두 개다. 라이브러리(내 곡 목록)와 연습 화면(플레이어). 연습 화면 하나에 파형·구간·드릴 컨트롤을 모은다.

라이브러리 내 곡 목록
· 최근 연습
· 구간 북마크
· + 곡 추가
트랜스포트 재생/일시정지 · 현재 시간 · 속도 · 키(반음) · 볼륨
파형 + 구간 드래그로 A-B 구간 선택, 저장된 구간이 색 밴드로 표시된다.
드릴 컨트롤 반복 횟수 · 반복 간격 · 점진적 속도 · 카운트인 · 메트로놈

그림 2 · 연습 화면 레이아웃(개념). 좌측 라이브러리 + 우측 플레이어.

구성 요소

  • 파형 뷰 — 클릭으로 이동, 드래그로 구간 선택. 저장된 구간은 반투명 밴드(amber)로 겹쳐 표시.
  • 구간 리스트 — 곡마다 여러 북마크("1절 고음", "브릿지")를 저장, 클릭 한 번에 그 루프로 진입.
  • 드릴 패널 — 현재 선택 구간에 적용할 반복 규칙. 프리셋으로 저장 가능.

04드릴 모드 스펙

단순 A-B 반복을 넘어, 실제 연습에 효과가 있는 파라미터를 붙인다. 이 표가 제품의 차별점이다.

기능파라미터기본값설명
구간 반복loopCount무한선택 A-B 구간을 지정 횟수만큼(또는 무한) 반복.
반복 간격gapSec0s반복 사이 쉬는 시간 — 원곡을 듣고, 그 틈에 내가 따라 부른다.
속도 조절speed1.0×0.5–1.0×로 느리게, 음정은 유지. 어려운 소절 해부용.
점진적 속도progressiveoff느리게 시작 → 반복마다 +step 빨라져 원속도까지. 근육 기억 훈련.
키 조절pitchSemitones0±6반음 이동, 원곡을 내 음역대에 맞춤.
카운트인countInoff루프 시작 전 "하나 둘 셋 넷" 들어가는 박 잡기.
메트로놈metronomeBpmoff박자 클릭을 원곡 위에 오버레이.
차별화 포인트 점진적 속도와 반복 간격(따라 부르기 틈)은 대부분의 무료 AB-루퍼가 갖지 않은 기능이다. 여기에 집중하면 "그냥 반복 재생기"와 확실히 갈린다.

05데이터 모델

네 개의 엔티티로 충분하다. M1에서는 모두 IndexedDB에 저장 — 원본 Blob과 파형 캐시까지 로컬에 둔다. M3 동기화를 위해 fileHash(기기 간 같은 곡 식별)와 updatedAt(충돌 해소)만 처음부터 넣어둔다.

// 곡 — 원본 mp3와 메타데이터
interface Song {
  id: string
  userId?: string         // M3 로그인 후에만 채워짐
  title: string
  artist?: string
  durationSec: number
  fileHash: string        // 내용 해시 — 기기 간 같은 곡 식별
  fileBlob?: Blob         // 로컬 원본(IndexedDB). 모바일은 없을 수 있다
  remotePath?: string     // M3: Supabase Storage 경로(선택 업로드)
  peaks?: number[]        // 파형 렌더 캐시(재계산 방지, 동기화 X)
  createdAt: number
  updatedAt: number       // 동기화 충돌 해소(최신 쓰기 우선)
  lastPracticedAt?: number
}

// 구간 — A-B 반복 지점이자 북마크
interface Region {
  id: string
  songId: string
  label: string           // "1절 고음", "브릿지"
  startSec: number
  endSec: number
  color?: string
  updatedAt: number
  deletedAt?: number      // tombstone — 삭제도 동기화되어야 한다
}

// 드릴 설정 — 한 구간을 어떻게 반복할지
// (독립 테이블이 아니라 Region 또는 프리셋에 embed — 구간과 함께 동기화된다)
interface DrillSettings {
  loopCount: number | 'infinite'
  gapSec: number                 // 반복 사이 쉬는 시간
  speed: number                  // 0.5 – 1.0 (피치 유지)
  pitchSemitones: number         // -6 – +6
  countIn: boolean
  metronomeBpm?: number
  progressive?: {                // 점진적 속도 상승
    startSpeed: number
    step: number
    targetSpeed: number
  }
}

// 연습 기록 — 통계/동기부여용
interface PracticeSession {
  id: string
  songId: string
  regionId?: string
  startedAt: number
  reps: number
  practiceSec: number
}

저장소는 얇은 래퍼(Dexie) 위에 리포지토리 함수로 감싼다 — M3에서 클라우드 백엔드를 붙일 때 이 경계만 바꾸면 된다.

저장 계층 — 로컬 우선, 클라우드는 거울

동기화의 목표는 PC에서 잡은 구간을 모바일에서 여는 것이다. 그런데 mp3 원본까지 전부 올리면 저작권·용량·비용이 한꺼번에 따라온다. 그래서 가벼운 데이터는 항상 동기화, 무거운 원본은 곡별 선택 업로드로 나눈다.

그림 3 · 동기화 구조. 실선은 항상, 점선은 사용자가 켠 곡만.

충돌은 최신 쓰기 우선(updatedAt 비교)으로 끝낸다 — 혼자 쓰는 도구라 이 이상은 과설계다. 삭제는 즉시 지우지 않고 deletedAt tombstone으로 표시해야 다른 기기에서 되살아나지 않는다.

06오디오 아키텍처

제품 품질을 가르는 부분. 루프 정밀도와 피치 유지 속도조절 두 가지가 관건이다.

속도 · 피치 독립 제어

  • 확정 AudioBuffer 경로 + soundtouchjs로 템포/피치를 독립 제어. 속도 조절과 키 조절을 동시에 정확히 준다. M1부터 이 경로로 간다.
  • 보류 — HTMLAudioElement.playbackRate + preservesPitch=true. 코드는 적지만 루프 정밀도·유연성이 떨어져 채택하지 않는다.
  • 교체 여지 — soundtouchjs의 음질이 부족하면 AudioWorklet 자체 구현으로 이 노드만 갈아끼운다. 그래프의 나머지는 그대로다.

파형 계산

큰 파일은 OfflineAudioContext 또는 Web Worker에서 피크를 계산해 메인 스레드 프리징을 피하고, 결과를 Song.peaks에 캐시한다.

09결정 사항

착수 전에 열려 있던 다섯 항목은 아래와 같이 정해졌다.

  • 결정됨 루프 정밀도 — 처음부터 AudioBuffer로 간다. HTMLAudio 임시 구현은 건너뛴다. 이음새 품질이 핵심 가치라, 나중에 교체하면 재생 상태·UI를 다시 만들게 된다.
  • 결정됨 속도/피치 엔진 — soundtouchjs로 M1부터 빠르게 붙인다. AudioWorklet 자체 구현은 음질 부족이 실제로 확인될 때만.
  • 결정됨 저장 · 동기화 — Supabase 채택. 구간·드릴 설정·기록은 항상 동기화하고, mp3 원본은 곡별 선택 업로드. PC에서 설정한 구간을 모바일에서 그대로 여는 것이 이 항목의 목표이자 M3 완료 기준이다.
  • 결정됨 PWA/오프라인 — 설치형으로 간다. 다만 급하지 않으므로 M3에 배치.
  • 결정됨 모바일 — 반응형 웹으로 커버. 네이티브는 수요 확인 후.

결정에서 파생된 남은 질문

  • 모바일에 mp3가 없을 때 — Storage에서 스트리밍할지, 통째로 내려받아 캐시할지. 정밀 루프는 AudioBuffer를 요구하므로 전체 다운로드 후 디코딩이 유력하다(3–5분 곡이면 감내할 만한 대기).
  • 같은 곡 식별 — fileHash로 매칭한다. 같은 곡이라도 인코딩이 다르면 별개 곡이 되고 구간 시간축도 어긋날 수 있다.
  • 무료 티어 한도 — Supabase Storage 한도를 넘길 때 업로드 곡 수를 제한할지, 유료로 넘어갈지. 우선 용량 표시 + 곡 수 제한으로 버틴다.
